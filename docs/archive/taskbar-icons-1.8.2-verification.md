# Windows 图标修复验证

适用范围：2026-10-31，当前 `1.8.2` 工作树上的 Windows 图标修复。该记录是验收证据，不替代 [图标规范](../reference/icons.md)。

## 根因

`tauri-codegen 1.4.2` 的 Windows 默认窗口图标入口只解码 ICO 第一帧。应用 ICO 从 16×16 开始排列，原 release 编译中间产物的图标 RGBA 为 1024 字节，即 `16×16×4`。窗口没有单独设置任务栏大图标，低分辨率默认图标会参与系统缩放。

应用与 Watchdog 母版均为 1024×1024，不需要以重新绘制、锐化或清理系统图标缓存掩盖加载问题。三种托盘母版和产物实际是 30×30，与原生窗口图标是不同路径。

## 修复边界

- Windows 主程序禁用 Tauri 的首帧默认窗口图标。
- `window/icons.rs` 从 EXE 的完整图标组资源 `32512` 按 DPI 加载，分别设置窗口小图标和任务栏大图标。
- 首次创建、恢复重建、DPI 变化共用该入口，句柄创建、替换、释放均位于窗口线程。
- 应用和 Watchdog ICO 包含 `16、20、24、32、40、48、64、72、96、128、256` 共 11 帧；favicon 同步包含常见的小图标尺寸。
- 母版图案、托盘 30×30 图案与状态含义、代理业务均保持不变。
- 同版本修复包通过 `PORTABLE_LABEL=icons-fixed` 单独命名，不覆盖旧包，也不替换正在运行的旧实例。

## 原生回读

测试在独立隐藏窗口中调用生产代码的图标加载入口，使用 `WM_GETICON`、`GetIconInfo`、`GetDIBits` 回读实际 HICON 位图，而非只检查文件头。两个窗口生命周期中各执行 `96→120→144→192→96` DPI 尺寸序列，每个状态检查大小两个图标，共 20 组回读。

| DPI | 小图标 | 大图标 | 像素与原生资源一致 | Alpha 背景保留 |
| --- | ------ | ------ | ------------------ | -------------- |
| 96  | 16×16  | 32×32  | 通过               | 通过           |
| 120 | 20×20  | 40×40  | 通过               | 通过           |
| 144 | 24×24  | 48×48  | 通过               | 通过           |
| 192 | 32×32  | 64×64  | 通过               | 通过           |

窗口销毁后，资源登记恢复到测试前数量。首轮回读数据位于 `.tmp/taskbar-icon-verification/26184/`，含 `native-icons.json`、原始 BGRA 和按原尺寸导出的 PNG；32、40、64 像素大图标 PNG 已实际查看。

## 限制

- DPI 序列测试使用真实隐藏 HWND 和指定 DPI 指标，不修改用户桌面缩放；没有将正在使用的主窗口搬到不同物理显示器上做人工验收。
- 实际 Tauri 创建和 DPI 事件入口已接入并通过编译；没有对用户运行实例注入 WebView 崩溃，也没有强制重启用户程序。
- 不修改系统图标缓存、用户固定到任务栏的快捷方式、系统代理、Windows 服务或防火墙。
- 即使原生资源与窗口回读均通过，最终桌面视觉效果仍需用户切换至新包后确认；复杂图案在 16 像素下本身存在细节上限。
